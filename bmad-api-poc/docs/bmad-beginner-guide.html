Build software with an AI team that writes things down

The BMAD Method turns your AI coding assistant into a small agile team: an analyst, a product manager, an architect, and a developer. Each one produces a short document, and the next one builds on it. You make the decisions. The AI does the drafting, coding and checking.

Each document is a plain file in your repo. The next step reads it, so you never have to re-explain your project to the AI.

The case for the POC

Why use BMAD instead of just chatting with an AI?

Plain prompting works for one-off snippets. It falls apart on a real project: the AI forgets earlier decisions, each endpoint gets built a little differently, and nothing is written down for the next person. BMAD fixes that with a fixed set of steps and a document at each step.

Seven words you'll see everywhere

Agent
A role the AI plays, with a name: Mary (analyst), John (product manager), Winston (architect), Sally (UX designer), Amelia (developer). Talk to one when you want that expertise.
Skill
A guided task the AI follows step by step, such as "create the PRD". Skill names start with bmad-. You run one by typing its name or asking in plain words.
Artifact
The document a skill produces. Stored in _bmad-output/ in your project.
PRD
Product Requirements Document: what the software must do, written as numbered requirements.
Epic / story
An epic is a large feature. A story is one small piece of it that can be built and tested in one session.
Acceptance criteria
The checks that prove a story is finished, written as "Given… when… then…". These become your tests.
Sprint status
A file that tracks every story through backlog → ready-for-dev → in-progress → review → done.
One-time setup · about 15 minutes

Set up your computer and project

You do this once per machine (steps 1–2) and once per project (steps 3–5). Tick the boxes as you go. Your ticks are saved in this browser only.

  1. Install the basic tools

    You need three free tools. Install each one, then run the check commands in a terminal. Each should print a version number.

    Node.js
    Version 20.12 or newer, from nodejs.org (pick "LTS").
    Python
    Version 3.10 or newer, from python.org.
    uv
    A Python helper that BMAD uses to run its scripts.
    # macOS / Linux: install uv
curl -LsSf https://astral.sh/uv/install.sh | sh
# Windows (PowerShell): install uv
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# Check all three
node --version
python3 --version
uv --version

  2. Install an AI coding tool

    BMAD runs inside the AI tool you already use. Pick one:

    Claude Code
    Terminal or VS Code. Install with npm install -g @anthropic-ai/claude-code, then run claude.
    Cursor
    Download from cursor.com.
    Copilot
    VS Code with the GitHub Copilot extension.

  3. Create a project folder

    mkdir task-api
cd task-api
git init

  4. Install BMAD into the project

    Run this inside the project folder. It asks a few questions. The defaults are fine, except you must pick your AI tool.

    npx bmad-method@latest install
    The installer asksWhat to answer
    Your nameYour name or your team's name. Agents use it to address you.
    LanguagesEnglish (or your preference)
    Output folderKeep the default, _bmad-output
    ModulesKeep BMad Method selected. Others are optional extras.
    Tools / IDEsSelect the AI tool you installed in step 2
    Experience levelBeginner, if you want agents to explain more

    Prefer no questions? This does the same with defaults for Claude Code. Swap claude-code for cursor or github-copilot.

    npx bmad-method@latest install --yes --modules bmm --tools claude-code --user-name "AIDLC Team"

  5. Check that it works

    bmad-help

    Open the project folder in your AI tool and type the line below. In Claude Code you can also type /bmad-help. If it answers with BMAD steps, you're ready.

    bmad-help: I'm new to BMAD. I want to build a small REST API. Where do I start?
Most important habit: start a new chat for each step. The documents carry the context forward. A long, single chat makes the AI slower and more confused.
Step-by-step recipes

Pick what you're building

Each recipe lists the skill to run, a prompt you can copy, and what you get. Start with the API recipe for the POC. UI and database work use the same flow with a few extra steps.

Example: a Task Management API. The finished version of every document below is in bmad-api-poc/_bmad-output/, so you can compare your results.

  1. Describe the idea

    bmad-product-briefMary, analyst
    Create a product brief. We need a REST API so internal teams can create, read, update and delete tasks, and dashboards and bots can integrate with it. This is a POC: no login and no database yet.
    You get
    product-brief.md: problem, users, goals, what's out of scope
    Tip
    Mary asks questions. Short answers are fine. Say "use sensible defaults" if you're unsure.

  2. Write the requirements

    bmad-prdJohn, product manager
    Create the PRD from the product brief. For each endpoint, define the fields and validation rules, pagination, the error response format, and the API version prefix.
    You get
    prd.md: numbered requirements (FR1, FR2…) and quality rules (NFR1…)
    Check
    Every error case has a status code. Ask John to "validate the PRD" when it's done.

  3. Decide how it's built

    bmad-architectureWinston, architect
    Create the architecture from the PRD. Stack: Python, FastAPI, Pydantic v2, pytest. Storage must be swappable, in-memory for the POC. Include the folder structure and the error format. Keep it short: decisions only.
    You get
    architecture.md: a short list of decisions every feature must follow
    Why
    This step is what keeps endpoints consistent. Don't skip it for a new service.

  4. Split into stories

    bmad-create-epics-and-stories
    Create the epics and stories list from the PRD and architecture. One story per endpoint, each with Given/When/Then acceptance criteria that name the status codes.
    You get
    epics.md: e.g. Story 1.1 Create, 1.2 Read, 1.3 Update, 1.4 Delete

  5. Check readiness and plan the sprint

    bmad-sprint-planning
    Run sprint planning.
    You get
    sprint-status.yaml. It also warns you if the plan has gaps.
    backlog→ready-for-dev→in-progress→review→done

  6. Build each story (repeat)

    Amelia, developer

    For every story, run these three in order. Use a new chat for each one.

    a
    bmad-create-story "Create the next story." It writes a story file with tasks and notes.
    b
    bmad-build "Build story 1.1." It writes code and tests, then runs the tests.
    c
    bmad-code-review "Run code review." Fix what it finds.
    Tip
    Use a different AI model for the review if you can. A second opinion catches more.

  7. Add API tests

    bmad-qa-generate-e2e-tests
    Create qa automated tests for the tasks API.

  8. Run it and look back

    bmad-retrospective
    pip install -r requirements.txt
pytest -q
uvicorn app.main:app --reload    # open http://127.0.0.1:8000/docs
    Let's retro epic 1.

Example: a web screen where users see and manage the tasks from the API. The flow is the same as the API recipe, with a UX step added and a human visual check at the end.

  1. Brief and requirements

    bmad-product-briefbmad-prd

    Same as the API track. Describe the screens in terms of what users want to get done, not how they look.

    Create the PRD for a web app where team members view, filter and update tasks. It uses our existing Tasks API (see the OpenAPI spec at /openapi.json).

  2. Design the experience

    bmad-uxSally, UX designer
    Let's create the UX design from the PRD. Cover the task list, the task detail panel, empty states, error messages, and mobile layout.
    You get
    DESIGN.md (how it looks) and EXPERIENCE.md (how it behaves)

  3. Front-end architecture

    bmad-architecture
    Create the architecture from the PRD and UX documents. Decide the framework, component structure, state management, how we call the API, and how we handle loading and errors.

  4. Stories and sprint

    bmad-create-epics-and-storiesbmad-sprint-planning

    Ask for one story per screen or component. Acceptance criteria should describe what the user sees.

  5. Build each story (repeat)

    a
    bmad-create-story, then bmad-build, then bmad-code-review, as in the API track
    b
    bmad-walkthrough "Walk me through this change." A person checks the screen and how to test it before merging.

Example: replacing the POC's in-memory storage with PostgreSQL. BMAD has no separate database skill. The architect makes the data design decisions, and each table or migration becomes a story.

  1. Capture the data needs

    bmad-prd
    Update the PRD: tasks must now be stored durably. Add requirements for data retention, expected volume, and who can see which tasks.

  2. Design the data model

    bmad-architectureWinston, architect
    Update the architecture for PostgreSQL. Decide: the tables and columns, keys and indexes, naming rules, the migration tool, how we roll back a migration, and how tests get a clean database. Keep the existing TaskRepository interface.
    You get
    Data-model decisions in architecture.md, which every migration story will follow

  3. One story per change

    bmad-create-epics-and-stories

    Ask for separate stories, e.g. "create tasks table", "SQL repository", "migrate existing data". Each acceptance criterion should include "the migration can be rolled back".

  4. Build and review each story

    bmad-buildbmad-code-review
    Run code review. Pay special attention to the migration: data loss, locking on large tables, missing indexes, and rollback.

  5. When the schema has to change

    bmad-correct-course
    Correct course: we need to add an "assignee" column to tasks. Update the PRD, architecture and stories.
Small change? Skip the planning. For one new endpoint or a bug fix, go straight to bmad-build: "Add a GET /tasks/search endpoint that searches titles." BMAD sizes the process to the work.
Showcasing the POC

A 15-minute demo for stakeholders

Show the documents first, then build something live. Building one new story on stage proves the point better than slides.

0–2
The problem. Open product-brief.md. One minute on why plain AI chat doesn't scale to a team.
2–4
The plan. Scroll prd.md and architecture.md. Point at one decision (the error format) and show it in the code.
4–6
Traceability. Open story 1.1. Show its acceptance criteria next to the tests that check them.
6–11
Live build. Run bmad-build on the new story below and let the audience watch it follow the architecture without being told.
11–13
Proof. Run pytest -q, then try the new endpoint in Swagger at /docs.
13–15
Status and questions. Ask "show sprint status". Share the scorecard.
Build this story. Story 1.5: Search tasks by title. As an integrating developer, I want GET /api/v1/tasks?q=<text> to return only tasks whose title contains the text (case-insensitive), so that I can find tasks quickly. Acceptance criteria: 1) q filters by title, case-insensitive. 2) q works together with status, limit and offset. 3) q longer than 100 characters returns 422 with code VALIDATION_ERROR.

npx or node is "not recognized"

Node.js isn't installed, or your terminal was open before you installed it. Install the LTS version from nodejs.org, close the terminal, open a new one, and run node --version.

My AI tool doesn't know the bmad- skills

Restart the AI tool so it picks up the new files. Check that the skills folder exists: .claude/skills/ for Claude Code, .agents/skills/ for Cursor and Copilot. If it's missing, run the installer again and select your tool.

"uv: command not found"

Install uv with the command in setup step 1, then open a new terminal. Some BMAD skills (sprint planning, for example) use it to run helper scripts.

The agent asks too many questions

Answer briefly, or say: "Use sensible defaults and list your assumptions at the end." You can correct the assumptions afterwards.

The AI ignored the architecture

You probably did several steps in one long chat. Start a new chat for the story. If it still drifts, run bmad-project-context to record the rule and the mistake, so every future session sees it.

Requirements changed halfway through

Run bmad-correct-course and describe the change. It updates the PRD, architecture and stories together instead of you editing each one by hand.
